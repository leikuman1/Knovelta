# MemoAgent Phase 1：MVP 开发与验收计划

> 项目：AI Database / MemoAgent，AI 原生个人知识管理 Agent。  
> 文档状态：开发计划，所有任务和验收结果均待实际实现后确认。  
> 范围：本地、单用户、单 Agent，先完成可靠的端到端闭环。  
> 主要依据：`MemoAgent_Development_Spec.md` 第 3–10、13 节及 `CLAUDE.md`。  
> 补充参考：`面试亮点/MemoAgent_STAR.html` 中明确属于 Phase 1 的设计；模拟指标不作为验收结果。  

## 1. 阶段目标

第一阶段交付一个可在本机运行的 Web App。用户通过自然语言记录、补充和查询个人技术知识，Agent 搜索已有笔记并提出变更，用户查看 Diff 后决定是否应用。

阶段结束时，必须能从空库在 UI 中完成：

1. 输入一条知识，保存原文，生成 CREATE Proposal。
2. 查看新增 Diff 并批准，形成可浏览、可搜索的笔记 v1。
3. 补充同一主题，生成针对该笔记的 UPDATE Proposal。
4. 查看修改 Diff 并批准，形成 v2，保留两个版本及其来源。
5. 提问并获得基于已提交笔记的回答，能打开对应笔记和原始来源。
6. 在 History 选择 v1，查看恢复 Diff 并确认，以新版本 v3 恢复 v1 的正文与来源集合。

可靠性与功能同时交付：拒绝不修改正文，过期提案不能覆盖新版本，失败可以恢复，回滚保留完整历史，笔记中的指令不能获得写入权限。

## 3. 技术方案与取舍

| 层 | 方案 | 选择理由与边界 |
| --- | --- | --- |
| 应用 | Next.js App Router + TypeScript | 同一工程提供页面、流式接口和受控后端 |
| UI | shadcn/ui 按需引入组件 | 优先完成对话、审批和历史操作 |
| Agent | Vercel AI SDK | 统一模型接入、流式输出和单 Agent 工具调用 |
| 模型接口 | OpenAI 兼容接口 | 通过环境变量配置 baseURL、apiKey、model，服务端使用 |
| 参数校验 | Zod | 校验工具参数、请求和 Proposal |
| 数据库 | SQLite + FTS5，优先评估 better-sqlite3 | 本地状态与检索共用数据库；初始化时验证 Windows 安装和 FTS5 支持 |
| 正文与历史 | UTF-8 Markdown 文件 | 满足本地可读、可迁移要求；采用提交记录协调双存储 |
| Diff | 小型文本 Diff 库 | 对服务端读取的基础正文和提案正文计算差异 |
| 验证 | Vitest + 少量 Playwright 端到端用例 | 服务层覆盖故障与状态，浏览器验证关键操作链路 |

仅使用 Node.js runtime。本阶段按单实例、本机文件系统设计，SQLite 和文件操作不放在 Edge runtime，也不部署到不提供持久磁盘的运行环境。

初始化时锁定实际可用的 Node.js、Next.js、AI SDK 和驱动版本，并提交锁文件。先验证驱动安装、SQLite FTS5 和一次临时文件替换，再开展业务开发。若驱动不适配，优先调整驱动选择，不新增独立数据库服务。

本阶段不引入 ORM、Redis、消息队列或独立 worker。短数据库操作使用事务；模型网络调用期间不持有数据库事务。AI 调用在请求内完成，失败后允许用户显式重试；跨重启自动续跑模型流程留待后续。

## 4. 总体结构与模块职责

应用分为页面与 API、Agent、业务服务、存储四层。Agent 通过窄工具面读取知识和生成 Proposal，只有受控业务服务能提交正文。

| 模块 | 职责 |
| --- | --- |
| Chat Service | 校验用户请求、保存原始输入、创建运行记录、驱动 Agent |
| Agent | 判断意图、搜索和阅读、生成答复或结构化 Proposal |
| Proposal Service | 校验并固化提案、生成 Diff、管理审批状态 |
| Note Service | 获取已提交正文、来源和历史版本 |
| Commit Service | 版本检查、文件写入、数据库与索引提交、幂等处理 |
| Recovery Service | 识别未完成操作、验证哈希、完成提交或恢复已确认版本 |
| Search / Evidence Service | FTS5 检索、提供版本化证据、解析与验证引用 |

## 5. 数据模型与不变量

### 5.1 核心实体

| 实体 | 核心字段与规则 |
| --- | --- |
| `sources` | `id`、`requestId`、`rawPath`、`inputType`、`createdAt`、`contentHash`、`status`；请求 ID 唯一，内容文件只创建一次 |
| `notes` | `id`、`title`、`wikiPath`、`currentVersion`、`contentHash`、`createdAt`、`updatedAt`；仅代表已提交状态 |
| `note_sources` | `noteId`、`sourceId`；当前已提交版本的来源集合 |
| `note_versions` | `noteId`、`version`、`title`、`contentHash`、`snapshotPath`、`proposalId`、`restoredFromVersion`、`createdAt`；笔记与版本号联合唯一 |
| `note_version_sources` | `noteId`、`version`、`sourceId`；精确保存每个版本的来源集合，回滚时使用 |
| `change_proposals` | `id`、`runId`、`action`、`targetNoteId`、`baseVersion`、`proposedTitle`、`proposedContent`、`contentHash`、`reason`、`status`、`createdAt`、`decidedAt` |
| `proposal_sources` | `proposalId`、`sourceId`；提案引用的真实原始来源 |
| `proposal_dependencies` | `proposalId`、`noteId`、`version`、`contentHash`；生成提案时实际依赖的已读笔记版本 |
| `write_operations` | `id`、`proposalId`、`noteId`、`fromVersion`、`toVersion`、`beforeHash`、`afterHash`、快照及临时路径、`state`、错误信息和时间；记录恢复依据 |
| `agent_runs` | `id`、`requestId`、`sourceId`、`intent`、`status`、`selectedTools`、`durationMs`、可选 usage、错误码及时间 |
| `audit_events` | `id`、`eventType`、`actor`、`runId`、`proposalId`、`operationId`、`noteId`、版本和时间；只追加 |
| `notes_fts` | 笔记 ID、标题和正文检索文本；仅索引最新已提交知识 |

原始全文保存在 Markdown，数据库中的检索文本属于可重建派生数据。初期使用整篇笔记索引，不建立独立分块系统。`related_notes` 在实际开展显式关联需求时再加入迁移。

### 5.2 必须始终成立的不变量

1. `raw` 不被模型或审批服务覆盖；拒绝提案不删除原文。
2. 没有用户批准记录，就不能产生已提交的 wiki 版本。
3. 一个 Proposal 的目标、基础版本、拟议标题、正文和来源固化后不可原地修改；修改需生成新 Proposal 并重新审批。
4. UPDATE / FLAG_CONFLICT 的 `baseVersion` 必须与批准请求的 `expectedVersion` 一致，并与提交时的当前版本一致。
5. CREATE 由后端分配 noteId，`baseVersion = null`、`expectedVersion = 0`，目标笔记必须尚不存在。
6. 同一 Proposal 最多形成一次提交；重复批准返回原结果，不重复追加版本。
7. 已提交的正文、哈希、版本、来源、FTS 和审计能够相互对应。
8. 每个已提交版本有不可变的完整 Markdown 快照及来源集合，包含 CREATE 产生的 v1。
9. 恢复历史版本会新增版本号，不修改已有版本或把当前版本号倒退。
10. 引用中的 noteId、version、sourceId 和摘录均来自本次实际读取的证据。

## 6. 原始输入与正文写入安全

### 6.1 原始输入先保存

用户消息进入处理流程后，先持久化 raw source。可将记录、提问和澄清统一保存，通过 `inputType` 区分；只有获批知识进入 wiki 和 FTS。

原始输入也采用可恢复步骤：

1. 用客户端请求 ID 去重，在 SQLite 建立 `pending` source 记录，分配 sourceId 并固定内容哈希。
2. 以该可信 ID 定位文件，使用独占创建写入完整原文并关闭文件。
3. 校验文件哈希后，将 source 标为 `ready`，再开始模型处理。
4. 失败或重启时检查 `pending` 记录：文件完整且哈希匹配则补齐状态；文件缺失或不完整则标记保存失败。保留已有文件供排查，不当作成功输入处理。

同一请求 ID 携带不同内容时拒绝复用。新请求提交相同文本仍可形成独立原始记录，不仅按内容哈希去重。原文落盘前不提示“已保存”，AI 失败时则明确告知“原文已保存，整理未完成”。

### 6.2 审批与正文提交

Markdown 与 SQLite 无法共用事务。采用持久化操作记录、不可变快照、单写入通道和重启恢复，保证可识别、可恢复的提交过程。

1. 后端读取固化 Proposal，验证用户审批、来源、依赖版本和 `expectedVersion`。
2. 在短 SQLite 事务内竞争提案状态和写入资格，持久化与提案内容哈希绑定的用户批准审计，记录操作 ID、前后版本及哈希。单实例全局串行执行正文提交，并通过数据库中的活动操作唯一约束防止重复占用；有未恢复操作时暂停后续正文提交。
3. 生成新版本的不可变快照与待替换文件，确保更新前的已提交快照完整，验证内容哈希并关闭文件句柄。
4. 再次核对目标版本与文件哈希，在同一文件系统内替换 wiki 文件。若当前文件与已知已提交哈希不同，停止提交并报告外部文件冲突。
5. 在一个 SQLite 事务内更新 notes、当前与历史来源、版本记录、FTS、Proposal 状态和成功审计，将操作标为 `committed`。
6. 返回最终提交结果；临时文件清理失败单独记录，不把它误报成正文提交失败。

文件替换成功、数据库尚未提交期间，普通读取通过 Note Service 返回上一已提交版本的不可变快照；FTS 仍只返回上一已提交版本。不能直接读取 wiki 并把它当成已完成的新版本。

原子替换的行为须在目标 Windows 环境验证；文件占用或替换失败应保留恢复状态，禁止使用“先删除目标再写入”的降级方式。该设计覆盖应用异常和重启恢复，磁盘损坏与断电耐久性取决于实际文件系统与刷盘策略，不能宣称绝对无损。

### 6.3 操作状态与恢复决策

操作状态采用 `prepared → file_replaced → committed`，失败时进入 `needs_recovery`，未产生提交的终止操作记为 `aborted`。状态字段仅是线索，恢复必须检查文件与快照哈希，处理“文件已经替换但状态尚未更新”的情况。

| 恢复时状态 | 处理原则 |
| --- | --- |
| wiki 仍为 beforeHash，数据库仍为旧版 | 验证快照和操作数据后继续；也可终止未生效操作，保留审计 |
| wiki 为 afterHash，数据库仍为旧版 | 依据已持久化且获批的操作补齐版本、来源和索引事务，不重复生成正文 |
| 数据库已为新版，wiki 与 afterHash 一致 | 视为成功，补齐清理并返回同一提交结果 |
| 数据库已为新版，但 wiki 缺失或哈希不符 | 用该已提交版本的可信快照恢复文件，再校验一致性 |
| wiki 不匹配已知前后哈希，或可信快照损坏 | 阻止进一步提交，显示需恢复；保留异常内容和审计，不能静默覆盖 |

启动时先运行恢复检查，完成前不接收新的知识写入。恢复入口与正常提交使用同一写入通道，恢复操作自身须可重复执行。自动恢复只继续已有用户批准的提交，不代替用户批准新内容。

Proposal 状态至少区分 `pending`、`applying`、`applied`、`rejected`、`stale`、`needs_recovery`。恢复后确定未生效的操作可回到待审批，但保留先前尝试记录；已生效操作只能返回已提交结果。

### 6.4 回滚规则

History 选择目标版本后，由后端生成 RESTORE 类型的系统提案，绑定当前版本和目标历史版本，展示完整 Diff、目标来源和恢复理由。用户确认后走同一提交服务。

例如当前为 v2，恢复 v1 会产生 v3：v3 的正文、标题和来源集合取自 v1，`restoredFromVersion = 1`；v1、v2、原始来源和历史审计继续保留。RESTORE 不向模型开放，批准时仍检查当前版本，避免恢复预览过期后覆盖新修改。

## 7. Agent 与工具契约

### 7.1 编排流程

写入采用受约束流程：保存原文 → 判断意图 → 检索 → 阅读候选与来源 → 生成提案 → 服务端校验 → 等待审批。查询采用检索 → 阅读 → 回答及引用。

Vercel AI SDK 负责流式响应和工具调用，应用控制当前阶段可用工具、步数和超时。首次检索为空时允许 CREATE；出现候选时，必须读取相关正文后才能提议更新。运行预算先设为最多 8 个模型步骤、12 次工具调用和 60 秒超时，作为待真实运行调整的配置，不作为性能承诺。

超限、模型失败或请求中断时保存运行结果，原始来源继续保留；不自动批准已生成的提案，也不依赖后台任务继续当前请求。

### 7.2 模型工具

| 工具 | 返回或作用 | 服务端限制 |
| --- | --- | --- |
| `search_notes(query, limit)` | 候选 noteId、标题、版本、片段及来源摘要 | 限制 query 长度和 limit，仅查询已提交知识 |
| `read_note(noteId)` | 正文、版本、来源及可引用证据 | ID 必须存在；UPDATE 前必须读取目标当前版本 |
| `read_source(sourceId)` | 原始记录及可引用证据 | 仅允许当前输入来源或本次已读笔记关联来源 |
| `create_change_proposal(...)` | 保存通过校验的 CREATE / UPDATE / FLAG_CONFLICT 提案 | 不能写正文或设置审批状态；每次运行最多生成一个待审批正文提案 |
| `list_note_versions(noteId)` | 历史版本摘要 | 只读，不提供恢复执行能力 |

本阶段暂不暴露 `get_related_notes`。批准、拒绝和恢复均为应用接口，模型不能调用。

### 7.3 Proposal 输入

结构化输入至少包含：

```ts
type AgentProposalInput = {
  action: 'CREATE' | 'UPDATE' | 'FLAG_CONFLICT';
  targetNoteId: string | null;
  baseVersion: number | null;
  proposedTitle: string;
  proposedContent: string;
  sourceIds: string[];
  reason: string;
};
```

后端补充 Proposal ID、runId、内容哈希、已读依赖版本、时间和初始状态，不接受模型自报的 `approved`、文件路径或审计身份。CREATE 的模型输入目标为空，实际 noteId 由后端分配。

服务端校验动作与目标组合、真实来源、已读版本和正文长度。更新使用完整的拟议 Markdown，Diff 由服务端计算；超过输入或正文上限时要求缩小内容，不截断后整篇覆盖。

FLAG_CONFLICT 的拟议正文应保留原说法、新说法、各自来源以及“尚待确认”的状态。提案展示双方证据，用户可以拒绝，模型不能静默消除分歧。

## 8. 检索与真实引用

### 8.1 FTS5 基线

索引标题和最新已提交正文，使用 FTS5 的相关性排序并按 noteId 去重；问答默认取 Top 5，工具 limit 设置服务端上限。

中文处理不能直接依赖默认分词器：初期采用 Node.js `Intl.Segmenter` 分词并为连续中文生成双字词项，将派生词项交给 `unicode61`；保留英文技术词、缩写及 `thread_id` 等 API 标识符词项。入库与查询使用同一规范化规则，保留原文用于展示和引用。

查询由服务端构造受限词项表达式并参数绑定，不把用户或模型文本直接当成 FTS 查询语法。空查询、无有效词项、超长输入和特殊字符有明确返回结果。用“检查点 / Checkpointer”“持久化”“thread_id”“缓存 / Prompt Caching”等中英文用例验证基线；同义词扩展只增加有用例支持的少量映射。

原始记录与待审批内容不进入默认知识检索；原文可以通过对应来源链接读取。索引重建只读取数据库登记的已提交版本，不扫描未知文件或把 staging 内容纳入知识库。

### 8.2 引用协议

Evidence Service 在实际读取时生成 evidenceId，绑定 noteId、noteVersion、sourceId、摘录和定位；原始来源摘录与整理笔记摘录分开记录。模型只返回这些 evidenceId，由后端生成 UI 链接，不接受模型提供的任意文件路径或来源 URL。

返回最终引用前检查：

- ID 和对应版本真实存在，sourceId 确实关联该证据。
- 摘录和行号能在指定版本的 Markdown 中核对。
- 证据来自本次实际读取，而非模型猜测的对象。
- 如果生成期间版本发生变化，重新取证，或明确展示引用使用的历史版本，不能标成最新版本。

UI 能同时打开所引版本的整理正文与对应原始记录。流式文本中的引用占位符在校验后解析；无效引用不渲染成可点击来源，并明确标记回答证据不足或要求重新生成。

确定性校验可以证明引用存在、版本及摘录匹配，不能证明引用支持每一句结论。语义支持度通过固定案例的参考证据和人工抽查验证。找不到材料或材料不足时，明确回复“未找到足够依据”，不补造个人笔记或结论。

## 9. 最小界面与接口

### 9.1 界面

| 区域 | 必须支持的操作 |
| --- | --- |
| Chat | 输入、流式回复、检索与读取状态、待审批提案入口、失败后重试 |
| Notes | 列表、关键词搜索、正文、当前版本和原始来源 |
| Change Review | 目标、动作、基础版本、理由、来源、标题与正文 Diff、批准和拒绝 |
| History | 各版本、时间、原因、来源、版本比较、恢复预览与确认 |

桌面优先使用笔记列表、主内容、引用或审批详情的布局；窄屏使用可切换面板。Markdown 作为不可信内容安全渲染，禁用原始 HTML 执行，禁止脚本 URL，用户输入不能进入可执行页面逻辑。

界面区分“原文已保存”“AI 处理中”“待审批”“已提交”“已拒绝”“提案过期”和“需要恢复”。提交按钮防重复点击，后端仍必须独立保证幂等。运行失败后已保存的 sourceId 可重新进入整理流程，避免重复保存原文。

### 9.2 接口契约

| 接口 | 语义 |
| --- | --- |
| `POST /api/chat` | 接收 message、requestId，保存原文后返回流式答复或 Proposal 事件 |
| `GET /api/notes` | 已提交笔记列表 |
| `GET /api/notes/:id` | 当前已提交正文、版本和来源 |
| `GET /api/sources/:id` | 原始记录详情，使用可信 ID 映射 |
| `GET /api/search?q=...` | 搜索结果及版本、片段 |
| `GET /api/proposals/:id` | 固化提案、服务端 Diff、来源和审批状态 |
| `POST /api/proposals/:id/approve` | 提交 expectedVersion，应用该固定提案 |
| `POST /api/proposals/:id/reject` | 将待审批提案标为拒绝 |
| `GET /api/notes/:id/versions` | 版本列表 |
| `GET /api/notes/:id/versions/:version` | 指定版本正文及来源 |
| `POST /api/notes/:id/restore` | 接收目标历史版本及 expectedVersion，生成恢复预览提案，确认走批准接口 |

错误结构统一包含 `code`、可读 message 和可追踪 requestId。版本冲突使用 HTTP 409，并提示重读、重新生成和重新审批，不能自动用旧提案覆盖；未知 ID 返回 404，非法输入返回 400。恢复尚未完成时，写入返回明确的暂不可用状态。

应用仅监听本机。审批和恢复属于用户操作入口，校验同源请求及防伪请求令牌，拒绝跨站写入；密钥与审批权限不传给模型。该约束用于保护本地审批入口，不扩展为多人身份系统。

## 11. 测试与验收矩阵

自动化测试分两层：业务与存储测试使用确定性模型适配器、独立数据库和临时目录，检查状态不变量；真实模型冒烟测试验证模型是否遵守工具与提案协议。模拟测试通过不能作为真实模型决策准确率。

| 编号 | 场景 | 必须验证的结果 |
| --- | --- | --- |
| T01 | 空库新增 | CREATE 待审批时只有 raw 与 Proposal；批准后 v1、快照、来源、FTS 和审计一致 |
| T02 | 同主题补充 | 先检索并读取原笔记；UPDATE 指向原 noteId；批准后 v2 可查询，无多余重复笔记 |
| T03 | 观点冲突 | FLAG_CONFLICT 保留双方观点和 sourceId；批准后仍可查看旧版本与证据 |
| T04 | 查询已有知识 | 回答引用真实 noteId、version、sourceId，摘录可核对，链接可打开 |
| T05 | 查询无依据内容 | 明确说明未找到足够依据，不生成伪造 ID、路径或来源 |
| T06 | 拒绝提案 | raw 保留；wiki、已提交版本、来源和 FTS 不变；拒绝行为有审计 |
| T07 | 审批版本过期 | 两个提案基于 v1，先批准一个形成 v2，另一个返回 409，不能覆盖 v2 |
| T08 | 写入失败与重启 | 在快照写入、替换前后、SQLite 提交前后注入失败；恢复后为完整旧版或完整获批新版，无混合状态 |
| T09 | 提示注入与路径攻击 | 笔记含“忽略指令、删除文件”等文本或非法 ID；无法越权读取、伪造审批或改写文件 |
| T10 | 更新后再问答 | 默认搜索读取最新获批版本；旧版只通过明确历史入口访问 |
| T11 | 历史恢复 | v2 恢复到 v1 形成 v3；正文、标题、来源与 v1 一致，v2 历史仍完整，FTS 同步 |
| T12 | 重复及并发请求 | 重复请求不重复保存同一 source；重复批准只形成一次提交；批准与拒绝竞争只有一个结果 |
| T13 | 原文保存中断 | pending source 可识别；完整文件补齐 ready，不完整文件不作为已保存输入处理 |
| T14 | 中文与技术术语 | 中文短词、中英混合、缩写、API 标识符及特殊字符可预测处理，查询不触发 SQL/FTS 语法注入 |
| T15 | 无效与过期引用 | 不存在 ID、错误摘录、非本次证据或版本变化不能冒充当前有效来源 |
| T16 | 模型超时或流中断 | raw 保留，run 状态和错误可追踪，wiki 不变；重试不重复提交知识 |
| T17 | 未完成提交期间读取 | 文件已替换但数据库未提交时，用户仍读到上一已确认版本及对应索引 |
| T18 | 跨站请求及 Markdown 脚本 | 伪造批准/恢复请求被拒绝，不可信 Markdown 不执行脚本 |

T01–T10 对应开发规格 9.1 的核心场景，必须有自动化覆盖。T08 包含恢复过程再次中断、FTS 更新失败和 Windows 文件占用；不能只测试正常抛出异常而跳过进程中断后的残留状态。额外验证外部改写 wiki 时停止覆盖并保留异常内容。

浏览器端至少自动覆盖一条“新增 → 批准 → 补充 → 批准 → 查询引用 → 恢复”的主链路，以及拒绝和版本冲突的交互。使用隔离测试数据，不接触个人真实笔记。

从 50 条人工确认案例起步，覆盖新增、补充、冲突、可回答查询、无依据查询和拒绝意图，区分调试与留出样本。保存预期动作、目标笔记、相关来源及语料版本；当前阶段以本地结果文件记录决策、Recall@5、错误合并案例、引用检查、耗时与可获得的 usage。无答案题不混入检索 Recall@5 分母，usage 缺失不记作 0。

安全性硬门槛为未授权正文提交次数 0、核心状态测试全部通过。决策质量和检索指标如实报告样本规模、失败数及分母，不预填准确率，也不把模型请求成功当作内容正确。LangSmith 对照实验和混合召回在 Phase 2 开展。
