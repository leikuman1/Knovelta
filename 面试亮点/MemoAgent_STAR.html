开发前规划 · 结合 Atomic 产品研究修订

MemoAgent 项目亮点

让零散记录形成有来源的主题知识，再在当前任务中被检索和主动带回。

用户通过自然语言记录与提问；单 Agent 负责查找、理解和提出变更，应用负责审批、执行与恢复。记录、整理、问答和回顾共享同一套来源与版本信息。

计划技术栈：Next.js · TypeScript · Vercel AI SDK · SQLite FTS5 · 本地 Markdown。向量检索、后台自动整理与定期回顾按阶段验证，采用可配置的 OpenAI 兼容模型接口。

LangSmith 评测口径 · 数字仍为模拟

自建评测集与可便捷取得的指标

模拟结果不等于实际评测结果。本节仅规划自建数据集与 LangSmith 展示方式。目前没有 Dataset、Experiment 或 Trace 实物，以下计数、耗时与 Token 均为模拟值，正式使用时必须替换。

面试时如何说明数据来源

应区分原始知识资料、测试输入、参考标注和运行结果。技术资料可来自自己的笔记及公开文档；依据这些资料设计新增、补充、冲突和查询案例，属于自建评测集。只有实际使用过公开测试集，并能说明名称、版本和修改范围时，才说采用公开测试集。

可以自己写测试输入，也可以用模型辅助生成后逐条审核；预期动作、目标笔记和相关来源必须人工确认。测试结果则应来自真实运行，不能依据预期效果填写，也不能把模拟结果归到网上数据名下。

实际完成后可这样回答：“这是围绕个人技术笔记场景自建的评测集。知识资料来自自己的记录和有出处的公开文档，我设计了新增、补充、冲突和查询案例，人工确认参考动作与目标笔记，并分开调试集和留出集。冻结语料后在 LangSmith 跑不同方案，分数、耗时、Token 和失败记录都能回到具体样本查看。”
如果实际用了模型辅助生成，再补充生成和人工审核过程。目前尚未执行，只能说上述评测是计划。

只保留五项量化指标

运行指标可直接追踪，质量指标需要定义评分逻辑
指标获取方式需要准备什么解释边界
平均根运行耗时实验中的 latency；按同类运行比较。根 Trace 包住检索、工具调用和生成，等待流消费完成再结束。不含用户审批等待、浏览器渲染和网络投递；单次模型耗时不等于完整 Agent 耗时。
总 Token实验中查看 token counts，按同一批根运行统计其模型子调用。模型接口返回 usage，AI SDK 集成正确上报输入 / 输出用量。同一模型调用只计一次，不把根聚合与子运行重复相加。兼容接口缺失 usage 时记缺失，不当作 0。
运行错误率按根运行的 error / status 筛选，错误数除以全部尝试数。异常如实记录，不将失败转换为普通成功输出；保留失败 Trace。运行成功不等于答案正确。预期版本冲突是业务结果，也不能当作异常错误统计。
写入动作及目标准确率简单代码 evaluator 返回 decision_correct 的 0 / 1 分，LangSmith 汇总平均。参考 action、targetNoteId，以及应用实际输出；字段名与空值规则固定。只评判提案选择，不代表正文已正确写入，也不证明系统具备恢复能力。
Recall@5代码 evaluator 对比 relevantNoteIds 与 retrievedNoteIds 前五，返回 recall_at_5。人工相关笔记标注，输出排序后的去重 noteId 列表。本例每题一个目标，命中即 1；多目标按交集数 / 标注目标数评分，无答案题不混入分母。

LangSmith 能展示自定义评分，但不会自动知道 MemoAgent 的正确动作或相关笔记。这里只增加两段确定性评分逻辑，不引入模型裁判。引用语义支持率、回顾有用率和故障测试通过率不再填模拟数字；相关内容审查及本地回归验收继续保留。

费用暂不展示。项目使用可配置的 OpenAI 兼容接口，模型名称与真实计费未必被平台正确识别；Token 上报是否完整也需先验证，不能把估算费用当作账单。

数据集和参考字段

保留小规模设置：计划整理 80 篇技术笔记、6 个主题，以及 100 条案例。写入和问答各 50 条，各取 10 条调试、40 条留出。问答留出中 32 条可回答、8 条无充分依据；32 条单独建检索测试 split，三种方案只在这个 split 比较 Recall@5、耗时与 Token。8 条无答案问题仍审查输出，本版不附评分数字。

每条数据保存来源 URL / 笔记 ID、语料版本、场景类型和生成方式，例如 manual 或 model_assisted_reviewed；同一事实的改写、相同更新链和近重复样本放在同一划分。调试后冻结规则与数据，在同一留出集比较，避免把答案泄漏到 Prompt。

任务Dataset 输入与参考运行输出评分规则
写入决策输入：message、fixtureVersion；参考：action、targetNoteId。action、targetNoteId。动作相同且目标相同计 1；CREATE / NOOP 按约定目标为空。执行异常或无输出计 0。
检索问答输入：question、fixtureVersion；参考：relevantNoteIds。retrievedNoteIds、answer、citations。取前五个去重笔记 ID 与参考集合比较。异常或空结果计 0；无答案题从本检索 split 预先排除。

写入实验仅执行到提案，不自动批准正文变更；每例读取指定 fixture，避免前一个样本影响后一个。质量 evaluator 对失败样本也须写入 0 分反馈；若平台默认跳过异常运行，应由评测程序补齐，并核对评分覆盖所有样本，不能直接用成功样本均值冒充整体准确率。

最小 LangSmith 使用流程

  1. 建立 Dataset。导入或创建 inputs、reference outputs 和 metadata，标记调试与留出 split，保存语料快照及来源；不把 LangSmith 叫作测试数据来源。
  2. 接入 AI SDK Trace。按实际安装版本采用官方集成，再用根运行包住完整提案 / 问答流程，验证工具子调用、usage 与错误状态都能回查。人工审批和后台等待不进入生成耗时。
  3. 添加两个代码 evaluator。用参考字段确定性计算 decision_correct 和 recall_at_5，人工抽查评分规则及异常样本覆盖，不调用额外模型评分。
  4. 跑固定实验并比较。以检索方案、Prompt 版本和模型作为实验 metadata，在相同留出 split 上运行，用 Compare 查看逐题分数、耗时、Token 与错误；评测器运行不计入应用 Token。
  5. 保存真实证据。留存私有 Experiment 链接、数据版本与失败 Trace；只有实际运行后再替换本节模拟值。无需为展示简历指标公开个人笔记。

面试中的关键区别：“自建测试集”说明你如何构造题目和确认参考答案；“真实实验结果”说明程序跑出了什么。可以自行设计题目，不能自行填写结果。LangSmith 提供记录、评分汇总与方案对比，结果仍需真实执行和可追查。

亮点一 · Phase 1 增量维护基础 / 后续主题综合候选

可追溯的主题知识维护

借鉴与改进：Atomic 将原始 atom 综合为带引用的 Wiki。MemoAgent 在既有 CREATE / UPDATE / FLAG_CONFLICT 提案上增加来源版本映射；后续来源更新或关联变化时，显式检查文章是否过期。

S · 情境
同一主题的资料会不断补充、出现分歧。只保存片段难以形成稳定知识；反复改写旧摘要又可能传播遗漏、丢失原意。
T · 任务
把零散输入维护成可阅读的主题笔记，保留原文和观点变化，并让每次正文修订有明确来源与审批依据。
A · 行动计划
原始输入只追加；单 Agent 先搜索与读取证据，再生成结构化提案。主题正文保存引用片段及所依赖的版本，新增材料产生增量修订，依赖变化触发重读或重建，用户通过 Diff 批准后生效。
R · 待验证
在 LangSmith 以 decision_correct 汇总动作及目标准确率，并观察耗时、Token 与运行错误。新增、补充、冲突和来源变化保留逐条案例；误合并、旧结论残留及主题重建通过实际输出审查，暂不另填效果比例。

实现方法

  1. 分层保存。raw source 不可变，wiki 是获批正文，versions 保存历史；避免把一次临时想法或引用他人的观点直接归为用户的长期结论。
  2. 先取证再提案。以搜索、readNote / readSource 和 createProposal 为窄工具面；约束来源 ID、目标 ID、baseVersion、动作和理由。证据不足时保留原文、请求澄清或不提出正文变更。
  3. 记录依赖。主题正文关联 sourceId、获批 noteVersion、chunkId / 内容哈希及引用摘录。主题或标签只有用户确认后才成为正式范围；自动标签先作为建议，保留人工覆盖记录。
  4. 区分新增与失效。新增资料可与现有文章、引用目录一起生成增量提案，必要时回读旧证据；获批笔记版本更新、主题成员变化或资料被明确排除时，使相关段落失效。原始 source 不由 AI 修改或删除。
  5. 拒绝过期提交。批准时验证目标正文版本和依赖来源版本；变化后重做提案。范围变化严重或多轮出现漂移时全量重建，再次审批；不直接累加旧摘要。

1. 有没有想过其他方法？3. 各有什么优劣？

方法优点代价适用条件
增量提案 + 来源依赖针对变化局部修订，保留稳定主题与审查依据。维护依赖、版本和重建策略，多轮可能漂移。文章持续维护，变更较频繁且确有复用需求。
每次全量综合逻辑清晰，可重新审视全部当前证据，是质量基线。重复输入较多，长主题需分层综合，全文表述可能反复变化。资料规模小、更新低频，或增量失效后的重建。
只追加原文 + 按需问答输入链路简单、历史完整，省去主题正文更新。重复与矛盾处理后移，每次问答重新综合，没有稳定主题文章。主要需要查找和回顾，较少直接阅读主题笔记。

编排也要比较：代码控制的固定检索—读取—提案流程更容易预算和调试；有界工具循环能动态补搜，但调用与延迟更不稳定。两者都可用 Vercel AI SDK，先用固定流程验证，再按真实漏搜案例决定是否增加循环。

2. 为什么采用当前方法？

项目需要稳定、可浏览的主题知识，增量修订与该目标匹配。但第一版先做现有笔记的可靠补充，再以小规模全量综合建立基线；只有更新成本和收益支持时，才增加主题级依赖与增量生成。固定流程与自主循环同样由准确率、误合并、调用次数和延迟比较决定。

面试参考：我希望笔记持续演化，同时能说明每次修改来自哪里。考虑过全量生成和只追加原文：前者简单，后者保留历史更直接。规划增量维护是为了保留稳定主题，但会先测全量基线；来源版本变化时重新取证和审批，避免长期摘要越改越偏。

验收证据：LangSmith 留出集的参考动作、目标及逐条评分；固定的新增、补充、同词不同义、矛盾和来源变更序列。误合并作为失败案例保留，正文、引用及获批快照另作实际验收，不只展示被接受的提案。

亮点二 · Phase 1 可靠写入 / 后续持久化处理增强

可恢复的处理与受控知识写入

借鉴与改进：借鉴 Atomic 保存与处理分离、阶段状态可见的体验，将异步任务与原有审批、版本和恢复机制接在一起。后台处理获得的是提案能力，真实正文修改仍由应用控制。

S · 情境
AI 调用会慢、失败或重复；笔记更新后旧任务可能晚到。用户审批期间正文也可能变化，Markdown 与 SQLite 还无法共用同一事务。
T · 任务
清楚区分已保存、处理中、待审批和已提交，在重复执行、中断或过期结果下保持获批知识可读、可恢复，并阻止未经批准的正文写入。
A · 行动计划
先可靠保存 raw，再持久化处理与提案状态；用任务唯一键、执行租约和输入版本控制阶段结果。用户批准确切提案后，以提交记录协调临时文件替换、数据库元数据与索引，保存快照、审计和恢复信息。
R · 待验证
在 LangSmith 查看异常根运行比例与失败工具 Trace；通过本地回归验证重复请求、过期审批、旧任务晚到、重启、写入失败与回滚后的状态。量化展示只保留运行错误率，恢复一致性以真实状态和测试记录证明，不能由无异常推出恢复正确。

实现方法

  1. 先确认落盘。原文持久化成功才提示已记录；任务创建中断时，从持久化原文扫描补齐。FTS 短操作可先同步完成，标签或 Embedding 真正带来长任务后再引入独立 worker。
  2. 持久化任务。唯一键包含对象、输入版本或哈希、处理阶段和配置版本。SQLite 事务领取任务，记录 attempt、leaseUntil 和执行标识；模型调用期间不持有数据库事务，提交结果时重新核对任务身份和输入版本。
  3. 提案与执行分权。工具白名单只开放检索、读取、生成提案；后端保存不可由模型声明的审批状态，并绑定目标、基础版本、提案内容哈希与用户操作。提案内容变更后原审批失效；独立审批接口也需防止被外部调用伪造用户批准。
  4. 协调双存储。获批提交先持久化 commitId、目标版本、快照及内容哈希，再生成并校验临时文件。通过单写入通道和目标版本检查替换正文，随后事务更新元数据、FTS 和提交状态；按步骤记录可恢复状态，不宣称跨存储原子事务。
  5. 保护读取和恢复。正文与数据库版本不匹配或提交未恢复时，按策略读取上一已确认快照或暂缓该笔记查询，不能当成已完成状态。重启结合文件哈希和操作记录补齐或恢复；重复批准只应用同一提交，回滚形成新的审计版本。
  6. 收窄执行边界。文件路径仅由可信 ID 映射到数据目录；读取、引用和写入分别校验对象与范围。笔记内容只作证据，不能授予权限；测试区分模型提出越权请求和后端实际执行越权操作。

任务可以被重复领取，目标是提交副作用可去重、状态可恢复；这不等于模型请求只执行或计费一次。原文、提交记录与快照之间仍需故障测试，不能用一个“原子重命名”概括全部可靠性。

2. 为什么采用当前方法？

正文作为本地文件是当前约束，SQLite 已存在，持久化任务和提交记录可以共享业务 ID、版本与审批信息。先跑通同步的可靠写入，再按长任务需要增加 worker；如果正文需求变成仅导出，应重新评估数据库权威存储，避免为了亮点增加恢复复杂度。

面试参考：我把保存、AI 处理、批准和提交拆成不同状态。比较过同步执行和内存队列；长任务需要跨重启恢复，所以规划持久化任务。写入部分仍是应用授权和版本检查，双存储则靠提交记录、快照与故障恢复协调。我会用中断与重复请求验证它，而不是承诺所有步骤恰好一次。

验收证据：故障前后原文、正文、快照、索引与任务状态；注入分别发生在任务领取、模型返回、文件替换、数据库提交等边界。拒绝提案后正文与对应索引不变，raw 可保留；用例总数和失败项完整报告。

亮点三 · Phase 1 检索引用基础 / Phase 2 对照评测

按范围检索与证据质量评测

借鉴与改进：借鉴 Atomic 的标签范围和片段引用，让同一检索与证据服务用于问答、主题维护和后续回顾。范围约束贯穿搜索、读取与引用，来源有效性和内容支持度分开验证。

S · 情境
技术笔记有中英文术语、版本号和概念改写。全库相似内容容易跨项目混入，旧版本也可能继续被引用；有效链接不一定支持答案。
T · 任务
在用户选择的主题范围中找回正确版本和证据，测清楚检索优化是否提高了最终回答质量。
A · 行动计划
建立中文和术语处理后的 FTS5 基线，再比较向量及 RRF 混合召回；服务端在搜索、按 ID 读取和引用提交时复查范围，引用保存笔记、来源及片段版本。用固定留出集分别评估召回和结论支持度。
R · 待验证
用 LangSmith 的 recall_at_5 反馈列比较按笔记去重的 Recall@5，同时查看平均根运行耗时、总 Token 与运行错误。引用支持、越界、旧版本和无答案问题继续人工或代码核查，暂不展示缺少评分与标注依据的比例。

实现方法

  1. 修好基础检索。Markdown 按标题、段落和代码边界分块，保留 noteId、version、sourceId 和定位信息。FTS5 明确中文处理方案，并测试缩写、别名、API 和版本号；不能直接把默认分词器当成充分基线。
  2. 限定范围和版本。第一版可使用明确的 noteId 集合；后续增加获批主题 / 标签。搜索过滤后，readNote、readSource 和引用校验仍复查范围，防止绕过搜索直接读 ID；默认只用已提交版本，历史查询显式选择历史范围。
  3. 做检索对照。后续用相同分块、语料与问题比较关键词、纯向量和混合方案；固定最终笔记 Top 5，记录各路候选数及预算。向量方案沿用既定可替换存储规划，不因 Atomic 使用 sqlite-vec 自动切换依赖。
  4. 校验三层证据。来源与定位是否存在、版本及范围是否符合本次任务、摘录是否来自对应内容；“是否支持这项结论”另作人工标注。来源变化时重取证，资料不足时说明未找到足够依据。
  5. 隔离评测数据。准备 50–100 条起始标注案例，含精确术语、中文改写、多项目同名、过期结论和无答案问题；调试集调查询与融合参数，留出集只评测。规定答案中的可核查陈述及支持证据，避免只查 ID。

1. 其他方法与 3. 优劣比较

方法优点代价适用条件
关键词 + 向量 + RRF结合精确词项和语义信号，排名融合减少分数尺度校准需求。双索引、去重与调参复杂，噪声也可能进入前列。单路存在互补漏召回，收益经对照验证。
关键词 + 别名 / 查询改写复用 SQLite，匹配原因容易定位。维护词表与中文处理，改写有偏移及调用成本。精确术语较多，适合作为初始基线。
纯向量 + 范围过滤适应不同措辞和概念检索。可能混淆相近 API、否定和版本，需维护 Embedding。自然语言语义查询较多，模型与分块质量可用。

2. 为什么采用当前方法？

先使用 FTS5 以复用 SQLite 并定位术语查询问题。混合检索只是待验证方向：若补齐分词、别名后仍有语义漏召回，再比较三组结果；质量相当时选更简单的方法。RRF 不是正确性的保证，范围过滤和引用支持评估必须独立保留。

面试参考：我会同时检查找没找到、能不能读、引用是否支持结论。考虑过增强关键词和纯向量，混合方案是为了检验两类信号是否互补。实验固定语料和测试集，在 LangSmith 用代码 evaluator 计算 Recall@5，并对比耗时与 Token；引用语义是否支持结论另审查，不把有效链接当成内容正确。

验收证据：标注数据、语料及配置版本、逐条检索排名、回答与引用；跨范围读取被拒和历史查询正常工作的测试。小数据集结果注明规模和局限，不外推为所有个人知识库的效果。

亮点四 · Phase 3 主动回顾候选

结合历史知识的主动项目回顾

借鉴与改进：借鉴 Atomic Reports 的 source scope、context scope 和引用策略。MemoAgent 先只做一个项目周回顾，以本期资料寻找历史想法的变化与未解决问题；增加逐条消费、重复抑制和反馈，验证是否真的帮助当前任务。

S · 情境
用户保存后遗忘，旧想法无法参与现在的工作；固定发送新增摘要可能只增加阅读负担，失败重试与重复提醒也会降低信任。
T · 任务
在明确的当前项目中，带回最多三条值得重新关注的内容，说明为何现在相关、依据在哪里，并能跳过没有价值的回顾。
A · 行动计划
本期来源与历史检索范围分开配置，单 Agent 复用已有搜索和读取工具，输出带新旧来源的独立回顾草稿；用持久化窗口、来源清单和幂等结果支持调度恢复，记录已展示内容与用户反馈。
R · 待验证
把单次回顾生成作为 LangSmith 运行，先记录耗时、Token 与错误状态；通过实际案例和本地回归验证来源窗口、重试与预算截断。内容价值保留真实审阅反馈，本版不量化有用率、重复比例或反馈覆盖率。

实现方法

  1. 先手动验证内容价值。用户指定当前项目，在应用内生成周回顾；内容包含新增认识、与旧观点的差异或未解决问题的新线索，均附引用。不强行凑满三条，没有足够价值时返回暂无回顾。
  2. 分开来源与上下文。sourceScope 指定本期已获批的笔记变更，contextScope 指定当前项目历史；原始输入可作为对应获批知识的证据。查询、读取和引用都检查范围。派生摘要与旧回顾默认不作为原始证据，避免循环综合。
  3. 引用策略显式化。只允许本期来源，或同时允许历史上下文；需要比较新旧观点时采用后者，并保留 sourceId、noteVersion、定位与摘录。发现“可能冲突”不自动裁定对错，用户决定是否生成知识修订提案。
  4. 持久化运行窗口。以获批变更事件序号定义来源，冻结本次上界与版本，为报告、配置版本和调度窗口建立唯一运行键。保存逐条资料状态，Token 预算放不下的留待后续批次，不能成功处理一部分就推进全部游标。
  5. 分开结果和投递。运行结果与引用以 runId 去重保存，失败重试原窗口；只有来源全部处理或被明确规则跳过才前移。保存投递状态，初期只在应用内展示；外部通知不是本项的默认条件。
  6. 用反馈抑制干扰。记录 sourceId、证据版本、主题、最近展示时间及有用 / 暂不相关 / 已处理反馈；来源版本或问题状态变化时允许重新出现。反馈先用于改进实际案例，无反馈不当作无用，本版暂不量化产品效果。

按时执行需要持续运行的本地进程或系统任务唤醒。应用关闭期间按已定义的合并窗口补跑，不承诺离线持续推送；不增加多个专职 Agent，也不自动批量重写知识库。

1. 其他方法与 3. 优劣比较

方法优点代价适用条件
本期变化 + 历史检索能解释旧内容当下的价值，发现观点变化与问题线索。检索、引用、任务状态和相关性评测更复杂。有持续项目，希望旧知识帮助当前工作。
固定周期新增摘要范围明确，实现与成本易控制。历史联系较弱，可能只是重复阅读新增内容。盘点近期信息摄取、生成简单日报或周报。
规则式间隔复习调度可解释，不必每次调用模型。需要记忆目标，难以发现新旧资料的语义变化。课程复习、考试知识点和稳定的记忆任务。

2. 为什么采用当前方法？

最初目标是让积累重新参与工作，历史检索因此有明确用途。先让同一批来源生成新增摘要与新旧关联回顾，按真实反馈和任务推进案例比较；如果用户主要要记忆知识点，规则式复习可能更合适。先验证应用内价值，再投入定时和通知。

面试参考：我把本期新增和可搜索的历史资料分开，是为了回答为什么这条旧笔记现在值得看。比较过摘要和间隔复习，它们分别适合盘点与记忆。回顾质量会用用户反馈验证，调度则用持久化窗口和逐条消费记录验证，避免重试后重复或跳过资料。

验收证据：固定窗口内的新旧资料、报告及引用；中断、重叠运行、空窗口与预算不足的回归记录；实际反馈及无反馈量。仅自用则明确单用户试用，不编造活跃用户、留存或业务增益。
